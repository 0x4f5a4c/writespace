# Module Ownership Map

> **Purpose:** Define clear ownership boundaries across `src/modules/` and `src/shared/`—which module owns which routes, PostgreSQL tables, Redis keys, and domain events.
> **Audience:** Internal backend developers designing features or refactoring across module boundaries.
> **Prerequisites:** Read [Repository Structure](repository-structure.md) and [Component Breakdown (C4 L3)](../architecture/components.md).

## Overview

Every feature module under `src/modules/` owns a specific slice of the `/api/v1` route tree (`src/routes/index.ts`) and a specific set of PostgreSQL tables (`src/db/schema/`). When one module needs to trigger behavior in another module, it either calls the target module's exported service facade (for synchronous operations like session creation or like toggling) or records a domain event in `outbox_events` via `eventPublisherService.recordInTransaction` (for asynchronous notification processing).

## Cross-module call rules

1. **Controllers never import another module's repository:** Cross-module calls go through the target module's service facade. The only cross-module controller reference is in `src/modules/auth/auth.routes.ts`, which mounts `UserController.updatePassword` on `PUT /api/v1/auth/update-password` as a backward-compatible alias for `PUT /api/v1/users/me/password`.
2. **Posts and Articles delegate engagement mutations to `interactionsService`:** `postService.likePost` / `sharePost` (`src/modules/posts/posts.service.ts`) and `articleService.likeArticle` / `shareArticle` (`src/modules/articles/articles.service.ts`) generate canonical URLs and delegate persistence and counter updates to `interactionsService.toggleContentItemLike`, `interactionsService.createShare`, and `interactionsService.createContentItemShare`.
3. **Domain modules never write directly to `notifications` or `notification_deliveries`:** Domain modules only call `eventPublisherService.recordInTransaction(tx, ...)` (`src/modules/notification/services/event-publisher.service.ts`) inside their database transaction, or call the legacy email facade `notificationService.send*Email(...)` (`src/modules/notification/notification.service.ts`) for authentication/account emails.

## Key decisions & rationale

- **Centralizing `security_events` persistence inside `src/modules/sessions/security-event.repository.ts`:** Both `auth` (`auth.service.ts`), `users` (`user.service.ts`), and `sessions` (`session.repository.ts`, `refresh-token.repository.ts`) call `securityEventRepository.create(tx, ...)`. Keeping `SecurityEventRepository` in one place guarantees that allowlisted security events (`AUTH_SECURITY_EVENT_TYPES` in `src/modules/notification/events/auth-security-event.types.ts`) always record their `security_events` row and their `auth.security_alert` outbox event in the same transaction.

## Gotchas & edge cases

- **Two follow toggle routes exist (`POST /api/v1/users/:id/follow` vs. `POST / DELETE /api/v1/interactions/users/:userId/follow`):** `UserController.toggleFollow` (`src/modules/users/user.controller.ts`) calls `followService.toggleFollow` (which toggles the follow state and returns `{ status: "followed" | "unfollowed" }`), whereas `InteractionsController.followUser` and `unfollowUser` (`src/modules/interactions/interactions.controllers.ts`) call the idempotent `followService.followUser` and `unfollowUser` methods (returning `{ followerId, followingId, isFollowing }`). Both paths use `FollowRepository` and lock both `users` rows in ascending ID order.
- **Unwired schema tables (`notification_user_settings` and `notification_suppressions`):** While `src/db/schema/notification-user-settings.ts` and `src/db/schema/notification-suppressions.ts` are exported in `src/db/schema/index.ts` and created by `drizzle/0000_initial_schema.sql`, no service or repository in `src/modules/notification/` queries or mutates them in v1.
